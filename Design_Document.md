# Design Document: Pending Template Update Notifications

## 1. Target Architecture

**Core idea:** separate the *fact that an engagement has a pending update* from the *engagement file itself*. We introduce an event-driven pipeline that maintains a lightweight, firm-scoped **Pending-Update Index**, populated asynchronously from events emitted by the two existing systems. No user-facing read path ever loads an engagement file.

### Components

- **Product Template Service (existing).** On publish of a new template version, emits `TemplateVersionPublished` to an event bus (EventBridge/SNS).
- **Engagement Management Service (existing).** Via hooks, emits:
  - `EngagementCreated`
  - `EngagementUpdateDecided`
- **Template Subscribers Index (new, shared, non-confidential).** A reverse index `template_id -> [{firm_id, engagement_id, region}]`, keyed by `template_id` as partition key, maintained by consuming `EngagementCreated`/`EngagementUpdateDecided`. Lives in the same account as the Product Template DB since it contains no client-confidential content (only template-to-engagement pointers, no financial data) — but see Security section for why pointers still need care.
- **Template Diff & Summary Cache (new, shared).** Keyed by `(template_id, from_version, to_version)`. A worker computes the structured JSON diff (existing capability) and renders it into a deterministic, human-readable summary (bullet list per changed section/field, generated by a rules-based renderer over the diff — *not* a free-form LLM rewrite of the diff; see AI usage notes). Cached once per version pair, reused across every firm/engagement affected — this is the key insight that keeps the fan-out cheap: the expensive "make this human-readable" step happens once per template update, not once per engagement.
- **Pending-Update Index (new, per data-residency region, firm-isolated).** One logical table per residency region (e.g., `us-pending-updates`, `eu-pending-updates`), partition key `firm_id`, sort key `engagement_id`. Each item: `base_version`, `pending_versions: [v2, v3, ...]` (accumulated chain), `latest_version`, `last_updated_at`. This is the **only** table the "engagement list" screen reads.
- **Fan-out Worker (new).** Lambda/consumer on `TemplateVersionPublished`. Queries Template Subscribers Index for `template_id`, batches updates (SQS → batched `UpdateItem`/`BatchWriteItem`) to append the new version onto each affected engagement's `pending_versions` in the correct region's Pending-Update Index. Idempotent (conditional write keyed by version, safe to replay).
- **Decision History (new, per-firm, append-only).** Written by consuming `EngagementUpdateDecided`. One row per decision: who, when, from/to version, firm. Feeds observability/audit; never mutated.

### Flow

1. Content team publishes template v2 → `TemplateVersionPublished`.
2. Diff worker computes/caches human-readable summary for v1→v2 (and any other version pairs needed).
3. Fan-out worker looks up all engagements on that template (any version), appends `v2` to each one's `pending_versions` in its home-region index. This is a bounded, async, retryable batch job — never on a user's critical path.
4. Firm opens engagement list → single query against their region's Pending-Update Index by `firm_id` → flags + rendered summaries pulled from the shared diff cache. Target p99 < 200ms regardless of firm size, since it's one partition-key query against a precomputed index.
5. User opens one engagement to decide → existing (slow, ~1 min) load path runs as it already does today, re-validates the current `latest_version` isn't newer than what was shown, applies/declines, emits `EngagementUpdateDecided`. The decision applies to the *entire* chain head (all-or-nothing across accumulated versions, not per-version) — a deliberate simplification given scope; see "Multiple accumulated updates" below. The handler re-checks the acting user's firm authorization before writing back (not just on the read path), updates the index to drop reconciled versions from `pending_versions` and advance `base_version`, and appends a Decision History row.

## 2. Implementation Plan

1. Define event schemas and wire hooks on template publish and on engagement create/decide (no behavior change to existing systems beyond emitting events).
2. Stand up Pending-Update Index tables (one per residency region) and Template Subscribers Index.
3. Build the Fan-out Worker + dead-letter queue + retry policy.
4. Build the deterministic diff-to-text renderer and the Diff/Summary Cache.
5. Build the read API for "engagement list with pending updates" (index-only reads, firm-scoped).
6. Update the existing accept/decline flow to re-validate against latest version and write back to the index + Decision History.
7. Backfill: for already-existing engagements, run a one-time job populating the Template Subscribers Index from current engagement metadata (template_id/version already stored on the engagement record, no full load required).

## 3. Testing Strategy

- **Contract tests** on event schemas (producer/consumer compatibility), using schema registry validation in CI.
- **Idempotency tests**: replay the same `TemplateVersionPublished` event twice, assert the index converges to the same state (no duplicate chain entries).
- **Fan-out correctness**: given N synthetic engagements subscribed to a template, assert all N (and only N) receive the pending flag; property-based tests for the "multiple accumulated updates" case (v2 then v3 arrive before a decision — chain must contain both, decision against `latest_version` must clear both).
- **Race condition tests**: decision in-flight while a new version publishes mid-flight — assert the engagement load path re-checks `latest_version` and surfaces the newly arrived version rather than silently dropping it.
- **Isolation tests**: attempt a cross-firm read/write against the Pending-Update Index with a token scoped to a different firm; must fail at the IAM/data layer, not just an application `if` check.
- **Diff renderer tests**: snapshot tests over representative template diffs, verifying the rendered summary is deterministic and traceable field-by-field to the underlying JSON diff (no invented content).
- **Load/chaos tests**: simulate a popular template update fanning out to thousands of engagements across many firms; verify batching, backoff, and that the read path latency is unaffected during a large fan-out.

## 4. Evaluation & Observability

- **Blast radius per update**: Fan-out Worker emits a metric `engagements_affected{template_id, version}` = count of index rows touched, available immediately after a publish, independent of whether any user has looked yet.
- **Coverage/liveness of the check**: because this is push-based (not a per-firm poll), "is it running for every firm" becomes "did fan-out complete for every subscribed engagement." A reconciliation job periodically compares the Template Subscribers Index against the Pending-Update Index's `latest_version` per engagement and emits a metric/alarm for drift; DLQ depth and consumer-lag metrics on the fan-out queue catch stuck processing before a customer notices.
- **Firm-level dropout detection**: the reconciliation job above only catches per-engagement drift, which would miss a firm whose `EngagementCreated` hook silently stopped firing entirely (nothing to compare against). A separate daily heartbeat compares `EngagementCreated` event counts per firm against the firm's known engagement roster from the engagement system, alarming on a firm that registers zero events when it should be active — this is the complementary check that catches a whole firm being silently dropped, not just a missed engagement.
- **Decision history**: Decision History table is directly queryable per firm (who applied/declined what, and when) — this is the audit trail requested, append-only and separate from both the engagement store and the template store. Exposed via a simple internal dashboard/query tool so "without waiting for a user to report it" has an actual place to look.
- **Tracing**: every event carries a correlation id (`template_id#version`) propagated through fan-out → index update → decision, so an engineer can trace one template update end-to-end in logs/traces.

## 5. Failure Modes & Tradeoffs

- **Eventual consistency**: the engagement list can lag a publish by minutes. Acceptable given weekly update cadence; made explicit rather than hidden.
- **Hot partition risk**: a template used by many firms makes `template_id` a hot key in the Subscribers Index during fan-out. Mitigate with write-sharding (suffixed sort keys) or moving the reverse index to a batch-friendly store (e.g., S3+Athena snapshot refreshed per publish) if a template's footprint grows very large.
- **Partial fan-out failure**: handled via DLQ + reconciliation job rather than assuming at-least-once delivery is sufficient; failures are visible, not silent.
- **Multiple accumulated updates**: resolved by keeping a chain, not just a "latest" flag, and letting accept/decline operate against the full chain head so no interim update is silently skipped; the diff shown to the user is base→latest (chained from the per-version cached diffs, flattened last-write-wins per field across the chain so a field touched in both v1→v2 and v2→v3 shows only its final value), not a confusing list of N separate changesets. The decision is deliberately all-or-nothing across the accumulated chain (no partial "apply v2 but not v3") — a reasonable scope simplification given the assignment excludes actually applying template content, but worth flagging as a tradeoff: a firm that wants v2's changes without v3's must wait and decide twice if updates are declined/applied one at a time by policy, or accept both together.
- **AI usage boundary**: an LLM may help *draft or phrase* the human-readable summary template once (a one-time, reviewed template per schema shape), but the actual field-level content shown to a non-technical user is rendered deterministically from the structured diff — never generated fresh per-diff by an LLM. This avoids hallucinated or omitted changes in a context where the apply/decline decision has real audit consequences. AI assistance is appropriate for drafting event schemas, test cases, and this document itself; it should not be trusted to summarize financial/engagement content directly, or to make the apply/decline decision.
- **Why not just poll each firm periodically?** Polling 100s of engagements × many firms to check "is my template newer" would reintroduce the 1-minute-per-engagement load cost at the polling layer — the entire design exists to avoid that. Push-based fan-out from the template publish event is what makes the "no synchronous engagement load" constraint achievable at this scale.
